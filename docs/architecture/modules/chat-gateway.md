# chat-gateway 模块

> 本文件描述 LLM 代理网关的职责、边界、对外暴露、依赖、接口契约。
> 全局架构见 [README.md](../README.md)；模块间交互见 [interactions.md](../interactions.md)。

## 1. 模块概述

| 属性 | 值 |
|------|-----|
| 业务领域 | LLM 请求代理：解析、选路、调用上游、流式回写、重试与日志 |
| 目录位置 | `handler/v1/`；`service/chat/`；`service/chatcore/`；`service/chatstats/`；`service/adjustment/`；`service/chat_facade.go`；`balancer/` |
| 主要职责 | 将客户端 OpenAI/Anthropic 兼容请求路由到可用供应商并记录结果 |
| 包形态 | **编排核心 + 旁路叶子包**（选路/重试/协议仍在 `service/chat`；Stats 与权重调整已拆出） |

## 2. 职责与边界

- **负责什么**：按协议 style 解析请求；解析模型名（真实/虚拟）；能力匹配；选择 `ModelWithProvider`；执行上游 HTTP（含重试）；流式/非流式处理；编排写入 `ChatLog`/`ChatIO`（经 chat 内 record 路径）与统计（经 `chatstats`）；失败/成功时触发权重/优先级调整（经 `adjustment`）；健康检查 `AdjustmentHooks` 由 `adjustment` 包级注入
- **不负责什么**：协议字段级互转细节（`protocol-transform`）；供应商 CRUD（`providers` 管理端）；关联/虚拟模型配置 CRUD；健康检查与模型同步调度；stats/权重算法本体（旁路包）
- **对外暴露**：`service` 门面中的 `Beforer`/`Processer`/`ProvidersWithMetaBymodelsName`/`BalanceChat`/`RecordLog` 等；`handler/v1` 的 `/v1/models`、`/chat/completions`、`/responses`、`/messages`
- **依赖谁**：`providers`、`protocol-transform`、`virtual-models`、`channel`（供应商内三层选路：端点→分组→凭据）、`repository`（持久层唯一入口）、`models`（实体/设置）、`balancer`/`chatcore`、`chatstats`、`adjustment`、`consts`

各子目录职责：
- `handler/v1/`：HTTP 接入与 style 分发
- `service/chat/`：端到端编排与注册表；日志落库编排；调用旁路包
- `service/credprobe/`：temp_unsched 惰性探活与恢复写（chat 只编排何时触发）；`completion_probe.go` 是 completion 探针（BuildReq→Do→归类→细节）的单一 owner，管理端各 completion 类测试端点只调 `RunCompletionProbe`，禁止再抄编排
- `service/credwrite/`：凭据健康写的有界异步队列（单 worker 串行落库、满时 drop-oldest 降级；chat/credprobe 经 SetHandlers 注入落库实现）
- `service/chatstats/`：Stats* 累加（无 chat 类型依赖）
- `service/adjustment/`：关联权重/优先级/连续失败；向 healthcheck 注入 hooks
- `service/chatcore/`：供应商选择算法与请求头（`BuildHeaders` 为 /v1 出站头唯一装配点，四层优先级链：入站白名单透传 < key 级头 < 关联级 customer_headers < providers 权威覆写；透传判据下沉 `common/headerpassthrough.go`，与 testapi 同源；#6）
- `balancer/`：加权随机纯算法 + 会话粘性表（`Affinity`，LRU+TTL 有状态单例，与 rrstate 同为进程内选路状态；`AffinityKey` 对话身份键派生）

## 4. 关键接口契约

| 契约 | 职责 | 定义位置 | 实现方 |
|------|------|----------|--------|
| `Beforer` / `Processer` / `StreamErrorWriter` | 按 style 预处理请求 / 处理上游响应 / 生成断流错误事件帧（Stage 30 W5 起注册面统一，handler 查表搬运） | `service/chat`（门面 re-export） | style 注册实现；注册了 Beforer 的 style 必须有 StreamErrorWriter（机械锁） |
| 提交门（commit-before-write） | 响应写给客户端之前验「内容可提交」：流式预读第一非空帧（判据 `common.SSEFrameContentError`，预读字节 Replay 回放逐字节等于原流）/ 非流式 JSON 载荷（`common.JSONContentError`；非流式收到 event-stream 判给错格式换下家）；失败回重试循环换下家、客户端零字节；首帧之后的错误属提交后语义，由 handler 断流收口 + `RecordLog` 清钉（见 §5） | `common/ssecontent.go`（错误形状判据单源） | `service/chat/chat_commit_gate.go`（attempt 内，先于任何客户端字节） |
| `BalanceChat` | 在候选供应商上执行带重试的转发；入参 `BalanceInput`、返回 `*BalanceResult`（含 `ServingModelWithProviderID`：本次响应实际由哪个关联提供，含故障转移后的赢家；提交后失败的清钉据此比对表内当前钉定，见 §5） | `service/chat_facade.go` | `service/chat` |
| `runProviderRetryLoop` | 在**单个候选池**上执行「选候选 → channel 三层选路（端点→分组→凭据）→ 尝试 → 淘汰」重试循环，产出 `retryLoopOutcome`（成功/穷尽/中止）；候选内嵌**组内凭据循环**（#13）：凭据级失败（429/5xx/鉴权/网络）写冷却或判停后刷新快照、`channel.RetryCredential` 锁组换 key 重试；`ErrNoCredentialAvailable` 时先惰性探活（#6-3）再决定是否组织级淘汰；`MaxRetry`/`ClientTimeout` 的取值已全局化（见 settings 模块「请求参数」，per-model time_out/max_retry 已移除）；总时长上限不在循环内维护（Stage 33）——由调用方挂在请求 ctx 的 deadline 上，`Ctx.Done` 同时覆盖「调用方撤走」与「网关掐断」（归因区分在 `chat_settlement.requestAbandoned`） | `service/chat/chat_retry_loop.go` | `service/chat`（包内，真实与虚拟路径共用） |
| `ProvidersWithMetaBymodelsName` | 按模型名解析候选供应商元信息（含虚拟模型分支）。**未选出供应商即失败**的四类出口（模型不存在 / 虚拟选模失败 / 虚拟跳过某真实模型 / 真实模型无启用供应商）经 `savePreProviderFailureLog` 建 ChatLog 行，失败原因与归因快照见 logs-metrics 模块；其中「真实模型无启用供应商」会区分严格能力匹配开关（开启时提示关联可能被能力需求筛掉）。**对外状态码**：模型不存在与「无启用供应商」两类配置态失败走 404（见 §5「失败状态码分类口径」），虚拟选模失败维持 500 | `service/chat` | `service/chat` |
| `chatcore.SelectByPriorityAndWeight` | 在关联列表上按优先级与权重选供应商；`preferID`（缓存亲和，2026-09-23）仅在「最高优先级档内（档 map 非空时）或无档全池内」且权重 > 0 时直返——优先级是管理员策略意志，粘性不越权；权重 0 的既有「不参与」语义粘性也不得复活 | `service/chatcore/` | `service/chatcore` |
| 缓存亲和（`balancer.AffinityKey` / `balancer.Affinity` / `balancer.Target`） | 对话身份键 = model + system 段 + tools + 首个用户回合的**规范化 JSON 语义值**摘要（长度前缀拼接 + sha256；字段顺序/注入字段不漂移，语义变化=新对话无害退化）；粘性表 LRU 4096 条 + 空闲 TTL 30min（`DefaultAffinity()` 进程级单例，内存态重启归零，与 rrstate 同口径）；`Target{ModelID, ModelWithProviderID, GroupID, CredentialID}` 字段 0 = 该层不钉，刻意无 EndpointID（端点同 wire 恒确定） | `balancer/affinity*.go` | `service/chat/chat_affinity.go`（唯一编排方） |
| `chatcore.BuildHeaders` | 生产转发（/v1 热路径）出站头构造，**唯一装配点**（禁止第二套拼装，方案 §2）。签名 `BuildHeaders(source, withHeader, keyHeaders, customHeaders, stream)`，**四层优先级链**（低→高，后写覆盖）：入站白名单透传 < key 级头 < 关联级 customer_headers < providers 权威覆写。① `with_header=true`＝白名单透传（判据 `common.PassthroughAllowedHeader` / `MergePassthroughHeaders`，与 testapi 同源）；② `stream=true` 置 `X-Accel-Buffering: no`；③ `keyHeaders` 来自 `middleware.CallerKey.Headers`（经 `ReqMeta.Headers` 整包透传，#6），显式通道不设头名黑名单（语法关＝apikeys/associations 两域写入闸共用 `common.SanitizeOutboundHeaders`）、与 `with_header` 正交；④ `customHeaders`（关联级）同名覆盖 key 级（渠道要求比客户端伪装更具体）；⑤ providers BuildReq 覆写 `Content-Type` 恒生效；**凭据头是死通道且两家同规则**（4b，唯一执法点 `providers/auth.go` `applyAuthHeader`）：供应商配置的认证方式（anthropic 键 `auth_type`、openai 系键 `openai_auth_type`——按协议拆方言，混合供应商互不翻转）选定后只发对应凭据头，对侧凭据头在构造点被删——`Authorization` 与 `x-api-key` 永不并发送达上游，key/关联级配置无法越过。契约测试：`TestBuildHeaders_FourLayerPriority`（单测钉三层）+ `chat` 包 `TestExecuteSingleProviderAttempt_KeyHeadersFourLayerPrecedence`（httptest 打真实上游收到的头，钉第四层） | `service/chatcore/headers.go` | `service/chat/chat_attempt.go`（真实与虚拟路径共用同一 attempt）|
| `balancer.WeightedRandom` | 加权随机选取 | `balancer/balancer.go` | 泛型算法 |
| `chatstats.Record*` | 请求/token/供应商/真实模型统计写入 | `service/chatstats/` | 同包 |
| `adjustment.Apply*` | 成功增权、失败衰减、连续失败 | `service/adjustment/` | 同包（兼 healthcheck hooks） |

## 5. 特殊约定

- **失败状态码分类口径（2026-09-27）**：`/v1` 代理链路的失败按「重试能不能变好」分两类回给客户端——① **配置态失败走 404**：该模型凑不出任何可用路由（模型不存在 / 无启用关联 / 全停用 / 严格能力匹配筛光 / 白名单对不上），对齐 OpenAI「model not found」口径，客户端不重试（重试不可能变好）；文案含调用方请求的模型名（调用方自有输入，非内部信息）与配置侧提示，落库错误文本同源（`noUsableProviderReason`）。② **重试穷尽走 502 Bad Gateway**：候选全部失败（真实路径 MaxRetry/池耗尽；虚拟路径全部真实模型穷尽），语义是「上游全挂」而非「网关自身故障」——与真 500（网关 bug）区分，客户端对 502 与 500 重试行为一致，监控侧可分类。两类的实现单源在 `client_request_error.go`（`newNoRouteForModelError` / `newRetryExhaustedError`），经既有 `clientRequestError` 机制在 `handler/v1/chat.go` 的 `errors.As(StatusCode)` 分支按自带状态码透传；**未选出供应商即失败**的落库留痕不变（仍经 `savePreProviderFailureLog`）。边界：客户端请求非法的 400 类透传维持现状；**网关总超时到点走 504 Gateway Timeout**（Stage 33，`newGatewayTimeoutError`——`mapAbortErr` 在 `BalanceChat` **唯一出口**把 `DeadlineExceeded` 映射为自带 504 的超时错误，真实/虚拟两路径全部出口共用、内层出口禁自映射；穷尽出口经 `retryExhaustedOutcome` 归因修正——末次尝试恰撞 deadline 时不记 502 的「上游全挂」，同样按超时归因。旧 `retry time out` / `virtual model global timeout` 裸错误落 500 的形态已移除）；流式已开流后的 SSE error 事件形状不含状态码（响应头已提交，改不了）。回归测试 `chat_failure_status_test.go` 三条（模型不存在 404 / 无启用供应商 404 / 重试穷尽 502）
- **入口总超时配置读失败处置（Stage 37，2026-10-02）**：`request_total_timeout` 读失败（DB 故障 / 解析失败 / Min 越界）→ 返回 60s 保守值并通过 `settings.LogReadSkip` 留痕（按设置项限频 60 秒/条，带累计压掉的次数），不 fail-open 静默取 schema 默认 600。读成功（key 存在或未设置）行为不变。常量 `conservativeRequestTotalTimeoutFallback = 60 * time.Second`（代码常量，不放 settings 表，避免与「默认 600」是两个不同语义的配置项混淆）。存量行迁移：启动装配经 `models.migrateRequestTotalTimeoutToCurrentDefault` 无条件 UPDATE `request_total_timeout` 行 value 列为 schema 默认值（按 AGENTS.md §0.1 + 项目当前阶段（仅开发者本人使用）约束，不写条件改写、不保护人工调过的值）；UPDATE 失败 slog.Warn + continue，不让 startup 挂。实现：`service/chat/chat_settings.go` `getRequestTotalTimeout`、常量 + 测试在 `service/chat/chat_request_total_timeout_fallback_test.go`、迁移在 `models/seed.go:migrateRequestTotalTimeoutToCurrentDefault`。

    ② **失败不是客户端撤走**。分两路：**读侧标记优先**——`MarkUpstreamReader`（`service/chat/upstream_read_error.go`）在错误产生处给「读上游」的失败套 `upstreamReadErr`，`IsUpstreamReadErr` 判定；其余走 `!isClientDisconnectErr`。**为何要标记**：`io.Copy` 的 error 不携带方向，而 `isClientDisconnectErr` 只能从类型反推、把任何非超时 `net.Error` 一律判为客户端断连，于是**上游 RST**（`*net.OpError`，`wsarecv forcibly closed`）被误判成客户端撤走 → 该清的没清（C2，真机 socket 实测）。标记必须打在 TeeReader **之外**（先包 reader 再 Tee），否则 tee 往日志管道的写失败会被误标成上游故障。

  - **为什么只收窄到提交后**：提交前失败会换家重试并在成功后改钉，本来就自愈；「任意上游失败就清」会让一次 429/网络瞬断丢掉该对话的提示词缓存，抖动一次即自毁特性。**为什么必须挂内层分支**：外层收口还兜着 `persistChatLog` 失败，那不是本次尝试的失败，挂那里会让「日志写库一失败就抹掉好端端的钉定」。**502（多家全挂）结构上到不了这里**——该路径在 `handler/v1/chat.go` 提前返回、根本不进 `RecordLog`（用户拍板：多家全挂不清，避免全体活跃会话集体失忆；`TestBalanceChat_ExhaustedKeepsSticky` 钉住这条，防止后人把清钉上移到 retry loop / `BalanceChat`）。清钉只摘**本对话**一条（`balancer.Affinity.DeleteIf`，同表其它对话原样存活；`Reset` 是全清，此路径禁用），留**恰好一行** `slog` 痕迹。
