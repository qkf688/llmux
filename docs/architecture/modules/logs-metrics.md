# logs-metrics 模块

> 本文件描述请求日志、ChatIO 与仪表盘指标域。
> 全局架构见 [README.md](../README.md)；模块间交互见 [interactions.md](../interactions.md)。

## 1. 模块概述

| 属性 | 值 |
|------|-----|
| 业务领域 | 请求可观测：日志查询清理、IO 详情、统计指标 |
| 目录位置 | `handler/logs/`；`handler/metrics/`；`service/chat` 内 `RecordLog`/落库编排；`service/chatstats/`（Stats 写入）；`repository/chat_log.go`、`repository/stats.go`；`models/retention.go`；实体 `ChatLog`、`ChatIO`、`Stats*` |
| 主要职责 | 管理端查询/删除/清理日志；ChatIO 详情；按天/小时/模型/供应商等指标；保留策略 |

## 2. 职责与边界

- **负责什么**：`ChatLog`/`ChatIO` 读删与清理；metrics 聚合查询；user-agents 等辅助查询；保留策略 `EnforceRetentionByOldestID`
- **不负责什么**：健康检查日志、模型同步日志（各自域）；发起 LLM 调用；模型/供应商配置
- **对外暴露**：`/api/logs*`、`/api/metrics*` 等 REST；`ChatLogRepo`/`ChatIORepo`
- **依赖谁**：`repository`（日志读写、保留清理，含 `ChatLogRepo.EnforceRetention`；统计读写经 `StatsRepo`）；`handler/metrics` 经 `repos().Stats` 只做展示计算，不再直读 `models.DB`；写入侧：日志落库编排在 `service/chat`（经 `repos()`），Stats 累加在 `service/chatstats`（经 `repos().Stats`）

## 3. 内部结构

```
handler/logs/          # 列表、详情、chat-io、删除、enrich
handler/logs/dto.go    # 对外响应契约（chatLogResponse / chatIOResponse）+ 映射
handler/metrics/       # dashboard 计数与时序
service/chat/*record* / chat_log_storage.go  # 日志落库编排
service/chatstats/     # Stats* 写入组合（叶子包，经 StatsRepo）
repository/chat_log.go
repository/stats.go    # 四张 Stats* 表（StatsTotal/Daily/Hourly/ProviderTotal）的 upsert 与聚合读
models.ChatLog / ChatIO / Stats*
models/retention.go
```

| `EnforceRetentionByOldestID` | 按策略裁剪旧日志 | `models/retention.go` | 同文件 |

## 5. 特殊约定

- **对外响应必须经 `handler/logs/dto.go` 的 DTO，禁止裸序列化 `models.ChatLog`/`ChatIO`**。理由是历史教训而非洁癖：`ChatIO` 曾直接 `httpresp.Success(c, chatIO)` 返回，GORM 模型的 Go 字段名就是 JSON key，改一个字段名（`LogId`→`LogID`）即破坏前端契约；`ChatLog` 曾用 `map[string]any` 手拼，漏写 `completion_tokens_details` 导致 reasoning_tokens 落库有值但 API 永不返回、前端类型声明成为谎言。结构体 DTO 让编译器兜住字段齐全，模型层字段改名不再波及 API
- API 字段一律 snake_case（含 `id` / `created_at` / `chat_io` 等，见 [conventions.md](../conventions.md)）；`raw` 六字段用 `*string`+`omitempty`——空字符串是合法值，必须与「include_raw=false 未返回」区分
- **头快照落库即脱敏 + 存量清洗（Stage 16 立项，Stage 26 扩两列，2026-09-27）**：请求与响应头快照均在写侧 marshal 前过敏感头剥除，判据单源 `common.MaskHeadersWithDenyList` / `MaskHeadersWithDenyListJSON`（`common/headerpassthrough.go`，deny-list = `Authorization`/`Cookie`/`x-api-key`/`Proxy-Authorization`/`Set-Cookie` canonical 五键）——敏感头**键保留、值整值 `****`**（保留「带没带这个头」的排障信息），非敏感头原样。**请求列**接线点唯一 = `service/chat/chat_attempt_log.go` 的 `captureRequestLogSnapshot`（第 6 参 `customHeaderKeys` 动态并入本次请求实际配置的自配头名——关联级 `customer_headers` + key 级自定义头键名并集，`customCredentialHeaderKeys` 提取；Stage 26 收口原「自配头名盲区」），全仓 RequestHeaders 只有这一个写入源。**响应列**接线点唯一 = `service/chat/upstream_body_limit.go` 的 `responseHeadersJSON`（成功路径 `updateRequestAndResponseLog` 与失败出口共用；Stage 26 落地前响应头明文落库）。**存量清洗**：启动装配时 `ChatLogRepo.SanitizeLegacyLogSnapshots`（`repository/chat_log.go`，两列统一入口；`main.go` 在 BootstrapAdmin 之后、`startBackgroundServices` 之前调用并传入 `collectConfiguredHeaderKeys` 现存自配头名全集，位置由 `main_startup_sanitize_gate_test.go` 机械门锁定）——游标分批（500/批）、幂等（已清洗行零改写）、坏 JSON 行 `slog.Warn` 跳过不阻断启动、只改值不删行、行级去重（同一行两列都命中算 1）；**实际改写行后追加 `VACUUM`**（物理抹除，Stage 16 risk-review C1 实测支撑；回归 = `repository/chat_log_sanitize_stage26_bytes_test.go` 双列字节扫描）。**清洗局限（文档化）**：请求列 extraKeys 以现存配置为界，已删配置的历史自配头名洗不到；响应列静态名单可洗全。契约测试：写侧 `service/chat/chat_attempt_log_sanitize_test.go` + `chat_request_headers_custom_mask_test.go` + `chat_response_headers_mask_test.go`、清洗 `repository/chat_log_sanitize_test.go` + `chat_log_sanitize_stage26_test.go`
- **调度明细四字段（`endpoint_protocol` / `endpoint_url` / `key_group_name` / `credential_note`）在 `service/chat` 建行时从选路结果 `Selection` 填充一次**（`executeSingleProviderAttempt` 的 logEntry）：失败出口全部走 `struct Updates`（零值跳过），不会用空串覆盖这些字段。`credential_note` 的取值规则是「Note 非空用 Note，否则 `KeyHash[:8]` 加 `#` 前缀」（见 chat 包 `credentialLabel`）——组内多 key 排查需要在日志里区分命中哪条 key，KeyHash 是不解密即可获得的稳定脱敏标识。`enrichChatLogs` 的格式转换判定同样消费 `EndpointProtocol`（与 chat 链路透传判定取数点同源），字段为空（S3-3 之前存量行）时判无转换
- **密钥归因两列（`api_key_id` / `api_key_name`）是调用方 key 的写入时快照**（多 api-key 方案 §4，#4-3）：传递链 `middleware.CurrentCallerKey(c)` → `handler/v1` 的 `newReqMeta` 翻译成 `models.ReqMeta.ApiKeyID/ApiKeyName` → **全部建行点**统一填充；失败出口是 Update 非建行，快照随行自带。`api_key_id` 为 `*uint`：null = 无归因（内部路径/存量行），DTO **禁 omitempty**（键恒在，前端可区分「无归因」与「后端漏返」）。名称是快照不是外键——key 改名/删除历史日志不回写（契约测试 `TestChatLog_AttributionSnapshot_ImmuneToKeyRenameAndDelete` 钉死，加 FK/JOIN/级联即红）；按 key 筛选与 api_key_id 索引均未做（方案 §4 定案，有需求再列）
- **请求编号列（`request_id`，Stage 17）**：请求 rid 的写入时快照，传递链 `middleware.RequestID`（值已带来源前缀：自生成 `gw:`+12hex / 沿用 `in:`+原值，见 framework-conventions §5「请求编号」）→ `handler/v1` 的 `newReqMeta`（gin context → `models.ReqMeta.RequestID`）→ **全部建行点**统一填充（`chat_attempt.go` 的 logEntry + `chat_log_storage.go` 的 preProviderFailureLog；retryLog 通道行由 logEntry 派生自动携带）；失败出口是 Update 非建行，struct Updates 零值跳过保证快照不被空串覆盖。DTO `request_id` 键恒在、**不用 omitempty**（string 无三态语义；存量行/内部路径空串 = 无编号，键在值空同 `api_key_id` 口径）；契约测试 `handler/logs/request_id_contract_test.go` 断响应体键在与值形（列表+详情双路径）
- **失败出口/建行写库一律不陪葬请求 ctx（Stage 17，审查回批后全写点收口）**：chat_logs 全部写库点经同一口径——派生表达式单源 `chatLogDetachedCtx`（`service/chat/chat_log_storage.go`，`context.WithoutCancel` + `chatLogWriteTimeout` 5s）。收口覆盖：① 失败出口回写 `updateChatLogByID`（`chat_attempt_log.go`，`Client.Do` 错误/转换失败/非通过状态码/体积闸超限/读体错误/成功路径 raw 回写 6 调用点 + **审查回批并入的 `chat_record.go` processer 错误分支**，此前该处直调靠调用方恰好传 `context.Background()` 保平安、无防线）；② 建行 `SaveChatLog`；③ 后处理路径 `persistChatLog`/`createChatIO`/`maybeClearRawOnSuccess`（`chat_record_persist.go` 内部派生，err 传播语义不变——该路径失败要中止后处理，不走 wrapper 的「仅 slog」口径）。**为什么**：超时/客户端断连正是请求 ctx 已死、最需要留痕的时刻，陪葬会让行停在建行值 `processing`（状态机见本节「请求日志状态机」条）——日志页把超时显示成「进行中」而等不到终态（状态机上线前更糟：建行即写 `success` 占位、成功出口不显式写终态，超时被计成成功），`maybeClearRawOnSuccess` 还会按行状态分流清理 raw。同口径延伸：**失败分支的设置读取**经 `withDetachedLogCtx`（`chat_attempt.go` 的 raw 开关/上限读取、`chat_attempt_error.go` 的错误体截断上限）——死 ctx 下 GORM 读设置退默认值，管理员配置恰在失败场景静默失效（审查回批 W2）。`updateChatLogByID` 对 `logID==0`（`disable_all_logs`）显式短路；写库姿势保持 struct Updates（零值跳过是调度明细/归因快照穿透的设计依赖）。回归：`upstream_body_limit_test.go` 的 deadline 用例断行终态 `Status=error` + rid 快照（改前实测红）+ `chat_log_write_detach_test.go`（cancelled ctx 两写点 + id=0 用例——后者锁「不误伤其他行」，短路分支本身不可由该用例区分）。**已知残余窗口**：detached 写自身失败/5s 内未完成时（SQLite 锁竞争、磁盘故障）行仍停在建行值 `processing`，观测面仅 `slog.Error`（带 log_id）——写库基础设施坏掉时无完美解，属明示权衡。**已知未收口邻接面**：同失败分支的 `applyProviderFailureAdjustments`（权重/优先级）与 `resetCredentialAuthFailCount` 仍用请求 ctx 直写（credwrite 主链已走 Background 队列不受影响）——已登记 find-issues，批次未定
- **请求日志状态机（`ChatLog.Status`，2026-10-09）**：建行（`executeSingleProviderAttempt` 的 `logEntry`）写 `processing`，终态由出口**显式**落库——成功出口 `RecordLog` 在 `persistChatLog` 之前置 `success`（processer 返回值不含 Status、struct Updates 跳零值，不显式写就会永远停在 `processing`），各失败出口写 `error`（现状不变）。**为什么建行值与终态分离**：改前建行即写 `success` 占位、成功出口不写终态，于是「进行中」与「已完成」在面板上无法区分，且进程被 kill / 断电时行永久停在 `success`、把「没记完」伪装成成功记录。**读写口径**：`maybeClearRawOnSuccess` 的判据是「状态为 `success` 才清 raw」（`processing` / `error` 一律保留）；列表/详情的状态列与筛选参数是透传；状态取值收在 `models.ChatLogStatus*` 常量单源（禁散落字面量）；`handler/associations` 的「最近 10 次请求成败」**排除 `processing` 行**（只统计已收尾请求：在途请求既非成也非败，画成失败会在长流式请求期间给出假结论；见 [associations.md](associations.md)）。**保留 `success` / `error` 键名**（前端筛选值与 Go 夹具依赖），不改成 `completed` / `failed`。本状态机后续再增两态——`canceled`（客户端主动断开，判据只认 `errors.Is(err, context.Canceled)`，不扩到整个 `clientSideFailure`：写回被上限掐断与坏管道不是「主动取消」）与 `interrupted`（进程非正常退出 / 关机丢弃，含启动兜底扫描）——落地时同步本节。**`canceled` 已落地（2026-10-10）**：判据单点 `service/chat.failureLogStatus`（与 `clientSideFailure` 同文件），两个状态写入点共用——提交前五个失败出口经 `buildAttemptFailureUpdate`（`chat_attempt_error.go`，含 `Client.Do` 失败与读体途中断开）、提交后经 `RecordLog` 的 processer 错误分支；两处各判一次会随失败类型新增而漂移，故收在一处。**覆盖面边界**：另有三类写入点刻意不走该判定（失败原因与请求 ctx 无关，判据不成立）——非通过状态码 `handleNonOKProviderResponse`（cause 就是上游状态码文本）、关机丢弃 `MarkLogUnfinished`（按「进程先走了」独立记 `interrupted`）、构建期失败（`savePreProviderFailureLog` 与 `ChatLog.WithError` 走的 retryLog 通道行）；只有「失败原因可能由调用方撤走引发」的出口才该接。**判据成立的前提**：本仓请求路径不自造 `WithCancel`（只有 `WithTimeout`，超时落 `DeadlineExceeded` 而非 `Canceled`），故链上出现 `Canceled` 即「调用方撤走」。回归：`service/chat/chat_log_status_canceled_test.go`（提交后矩阵四格含两类反例 + Do/读体两条真实路径，两者分属不同失败出口）。**已知取舍**：流式中客户端断开若先表现为写侧失败（对端 RST、`write: broken pipe` 这类 `*net.OpError`），链上没有 `Canceled`，仍记 `error`——口径只认 `Canceled`，这是既定结果。

- **`interrupted` 已落地（2026-10-10，分片 #3）**——**产生路径**：建行写 `processing` 后终态要靠各出口落库，进程被 kill / 断电时出口一个都跑不到，行永久停在建行值；按 AGENTS §0「当前代码仍持续产生」，故配常驻启动兜底而非一次性清理。两个写入点合起来才是完整的「进程先走了」口径：① **关机丢弃** `service/chat.MarkLogUnfinished`（bgtask 排空后仍未写完，终态由 `error` 改写为 `interrupted`——关机是本机行为、供应商已完整产出，记 error 会冤枉上游）；② **启动兜底** `repository.ChatLogRepo.MarkUnfinishedLogsInterrupted`（`main.go` 装配段，紧随另两处清洗之后，`UPDATE ... WHERE status = 'processing'` 单条改写、只改状态不删行、幂等）。**判据零误判的前提**：兜底必须早于 `startBackgroundServices` 与流量，此刻库里的 `processing` 行必然来自上一次进程；挪到之后会把本进程的在途请求误判成上次的中断残留（位置门 `main_startup_interrupted_log_gate_test.go`）。**刻意不用时间阈值**（与 axonhub 的 `created_at < now - 1h` 不同）：那是多实例滚动重启场景的需要，本机单进程 + SQLite 下加阈值只会漏掉「刚崩的进程留下的行」。失败只 `slog.Error` 不阻断启动（与另两处清洗同姿势）。回归：`repository/chat_log_interrupted_test.go`（只改 processing 行 / 终态行逐字零改写 / 行数不变 / 二次执行返回 0）、`service/chat/chat_log_discard_test.go`（关机丢弃终态）、`handler/v1/chat_log_attach_test.go`（丢弃窗口端到端）。**读点现状**：`maybeClearRawOnSuccess` 只认 `success` 才清 raw，故 `interrupted` 与 `error` 同待遇、保留现场；`handler/associations` 的「最近 10 次请求成败」已于分片 #4 收敛为**只统计 `success` 与 `error`** 的白名单（`canceled`/`interrupted`/`processing` 三态一并排除，既不占名额也不画成失败）。状态机基座回归：`service/chat/chat_log_status_machine_test.go`（成功出口落 `success` + 上游阻塞时该行停在 `processing`）。

  - **分子必须是 completion**：用 `total_tokens` 会把 prompt 算进「每秒生成」，长上下文下数值被放大数千倍（现场一条 prompt 48 万 / 生成 234 的请求算出 7.8 亿）。
  - **分母必须是整段耗时**（`elapsed = time.Since(start)`，与面板「代理耗时」同源，都以 `ReqStart` 为零点）。**不要改回「首帧 → 末帧」的 `chunkTime`**：上游成批下发（憋到最后一次性 flush，或对 stream 请求回整体 body）时该窗口塌到亚毫秒级、商爆炸；且那类请求不分供应商、不分流式与否地偶发存在，没有可靠阈值可切。四个参考项目（new-api / axonhub / octopus 二开）分子一致用 completion，分母是否用生成窗口则各家不同且四种兜底互不相同——**无公认口径**，别照其中一家反推。
  - **语义如实转述**：首包等待计入分母，故本值答「这次请求多快」，**不是**「模型吐字多快」；比较两个模型的生成速度时它答不了。上游未给 completion 时本值为 0（与 usage 各处「没拿到即 0」一致，面板「Token 使用」栏的输出格同时为 0）。
