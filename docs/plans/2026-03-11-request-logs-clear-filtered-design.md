# 请求日志：清空筛选结果（设计）

日期：2026-03-11

## 背景

当前“请求日志”页面只有“清空所有日志”，它调用 `DELETE /api/logs/clear`，会无视筛选条件直接清空全部请求日志与对话记录。

用户需求：当筛选出成功日志（或其它筛选条件）时，希望能“一键删除所有符合当前筛选条件的日志”，而不是清空全部。

## 目标

- 在“请求日志”页面新增“清空筛选结果”入口。
- 删除范围为“当前筛选条件命中的全部日志（跨分页）”，并同步删除关联 `ChatIO` 记录。
- 误操作保护：当没有任何筛选条件时，不允许执行该操作（避免等同于清空全部）。

## 非目标

- 不改变现有“清空所有日志”的语义与接口。
- 不新增前端循环分页删除（仅走后端一次性删除）。

## API 设计

### 新增接口

- Method: `DELETE`
- Path: `/api/logs/clear-filtered`
- Query 参数（与列表保持一致）：
  - `provider_name`
  - `name`
  - `status`
  - `style`
  - `user_agent`
- 响应：
  - 成功：`{ deleted: <int64> }`（保持现有 `common.Success` envelope）
  - 失败（无筛选条件）：`400 BadRequest`

### 行为约束

- 当所有筛选参数均为空时返回 `400`，避免误删全部日志。
- 在事务中删除：
  1) 删除 `chat_io`：`WHERE log_id IN (subquery chat_logs.id by filters)`
  2) 删除 `chat_logs`：`WHERE id IN (same subquery)`

## 前端交互

- 保留现有按钮“清空所有日志”（危险操作）。
- 新增按钮“清空筛选结果”：
  - 当筛选条件全部为 `all` 时置灰（同时后端也会 `400`，双保险）。
  - 点击弹出确认对话框：
    - 显示当前筛选摘要（如：状态=成功、提供商=xxx…）
    - 提示“跨分页删除、不可恢复”
  - 成功后 toast：`已清空筛选结果 ${deleted} 条日志`
  - 成功后清空当前选中项；必要时回到第 1 页并刷新列表。

## 测试

- Go 单测覆盖：
  - 无筛选参数调用 `ClearFilteredLogs` → 返回 `400`
  - `status=success` 删除成功日志：
    - `chat_logs` 中仅 success 被删除，error 保留
    - 关联 `chat_io` 一并删除
